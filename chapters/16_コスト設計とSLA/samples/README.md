# 第16章 コスト設計とサービス品質 ── サンプルコード

本書第16章の「1リクエストのコストを積み上げ、必要なサービス品質を見合う費用で維持する」という設計を、手元の数字で確かめられるサンプルです。次の3つをAPIキー・ネットワーク・外部ライブラリなしで実行できます。

1. 1リクエストのトークン内訳から、1日・月間のコストを試算する（本文 16-2）
2. プロンプトキャッシュのヒット率で費用がどう変わるかを見る（本文 16-4）
3. レート制限に合わせた待機と再試行で、バーストがならされる様子を見る（本文 16-5）

`_common.py` のモデル単価は、本文の表16-1-1と同じ**2026年7月29日時点**のスナップショットです。料金とモデル名は変わるため、実際の試算では最新の公式料金に置き換えてください。トークン数は本番ではAPIレスポンスの `usage` から取得します。

## 収録ファイル

| ファイル | 本文の節 | 確かめられること | APIキー・外部ツール |
|---|---|---|---|
| `_common.py` | 16-1〜16-5 | 料金スナップショット・コスト計算・キャッシュ試算・スロットリングの実装（各スクリプトが共通利用） | 不要 |
| `16-2_token_cost.py` | 16-2 トークンコストの試算モデル | 本文 表16-2-1と同じ、設計変更による1件・1日・月間コストの違い | 不要 |
| `16-4_cache_simulation.py` | 16-4 プロンプトキャッシュ | ヒット率を変えたときの、キャッシュ有り／無しの費用差 | 不要 |
| `16-5_throttling.py` | 16-5 同時実行制御とレート制限 | バーストで来た依頼が上限内で待機・再試行され、ならされて処理される時系列 | 不要 |
| `try_token_cost.py` | ―（本リポジトリ限定の追加教材） | 自分のトークン数・件数・モデルでの1件→1日→月間の試算 | 不要 |

## 前提

- Python 3.10 以上（動作確認は 3.12）。すべて標準ライブラリだけで動くため、`pip install` は不要です（`requirements.txt` は本番移行時のメモのみ）。
- 本章のサンプルにAPIキー・外部サービスを使うものはありません。

## 実行手順

`samples/` ディレクトリ直下で実行します（`_common.py` を読み込むため）。

```bash
cd samples
python 16-2_token_cost.py
python 16-4_cache_simulation.py
python 16-5_throttling.py
```

3本とも乱数を使わない決定的な計算なので、出力は毎回同じです。

- **`16-2_token_cost.py`**：本文 16-2 と同じ条件（入力6,000・出力1,000トークン、1日1,000件、30日）の試算です。主な出力は次のとおりで、本文の表16-2-1と同じ数字になります。

  ```text
  基準：Terra              1件=$0.0300 1日=$30.00 月間=$900
  出力を500へ              1件=$0.0225 1日=$22.50 月間=$675
  入力4,000をキャッシュ     1件=$0.0210 1日=$21.00 月間=$630
  すべてLuna               1件=$0.0120 1日=$12.00 月間=$360
  80% Luna / 20% Terra     1件=$0.0156 1日=$15.60 月間=$468
  ```

  見どころは行どうしの比較です。出力削減・キャッシュ・モデル切り替え・振り分けのどれが月額をいくら動かすかを、同じ条件のまま横に並べて確認できます。
- **`16-4_cache_simulation.py`**：前置き4,000トークン×10,000リクエストについて、ヒット率0〜95%でのキャッシュ有り／無しの入力コストと削減率が表になります。見るべきは両端です。ヒット率0%では書き込み単価（割高）だけを払うためキャッシュ無しより高くなり、ヒット率が上がるほど削減率が大きくなります。「キャッシュは張れば得」ではなく「当たれば得」であることが数字で分かります。
- **`16-5_throttling.py`**：6 RPMの上限に12件がバーストで到着した時系列が表示されます。最初の6件は満タンの枠で `t=0` に送信され、7件目以降は10秒ずつ待って `t=10, 20, ..., 60` 秒に送信されます（待たされた件数 6/12、全件で60.0秒）。上限を超えた分が「待って再試行」でならされる、という本文 16-5 の挙動の骨格です。

## 自分で確かめる

- **自分の条件で試算する**：`try_token_cost.py`（本リポジトリ限定の追加教材）に、自分のトークン数・件数・モデルを引数で渡せます。

  ```bash
  python try_token_cost.py --input 6000 --output 1000
  python try_token_cost.py --model gpt-5.6-luna --input 2000 --cached 4000 --output 500 --per-day 200 --days 20
  ```

  実際のエージェントで測った `usage` の値（1依頼あたりの合計トークン）を入れると、自社の月額の当たりを付けられます。
- **単価を最新の料金に差し替える**：`_common.py` の `PRICING`（19〜26行目）を書き換えるか、同じ形式で自分の使うモデルを追加します。追加したモデルは `try_token_cost.py --model` の選択肢に自動で現れます。
- **試算の前提を変える**：`16-2_token_cost.py` の `per_day`・`days`（13〜14行目）、比較ケースの `cases`（17〜24行目）、振り分け比率の `0.2`／`0.8`（38行目）を書き換えると、表16-2-1を自分の前提で作り直せます。
- **キャッシュの前提を変える**：`16-4_cache_simulation.py` の `prefix_tokens`・`requests`・`model`（14〜16行目）と、比較するヒット率の並び（22行目）を書き換えます。前置きが短いときや利用回数が少ないときに、削減額がどこまで縮むかを確かめてください。
- **レート上限を変える**：`16-5_throttling.py` の `num_requests`・`rpm_limit`（14〜15行目）を、自分の契約ティアの上限と想定バースト量に合わせると、全件さばくのにかかる時間がどう変わるかを見られます。

## うまくいかないとき

- `ModuleNotFoundError: No module named '_common'` → `samples/` ディレクトリ直下で実行してください。
- 起動直後に構文エラーになる → Pythonが3.9以前の可能性があります。`python3 --version` で3.10以上を確認してください。
- Windowsで日本語が文字化けする → 環境変数 `PYTHONUTF8=1` を設定して実行してください。
- `KeyError` になる → `PRICING` にないモデル名を指定しています。`_common.py` の `PRICING`（19〜26行目）にあるキーを使うか、単価を追加してください。
- 試算が実績と合わない → 本サンプルは構造を見るための試算モデルです。実際の課金はモデルの呼び出し回数・キャッシュ方式・重いケースの分布で変わるため、本番ではAPIレスポンスの `usage` と請求実績で突き合わせてください（本文 16-2）。
